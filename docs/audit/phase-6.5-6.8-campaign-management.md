## 2. 6.5 — campaign database

Additive (no existing table, grant or policy changed). After applying all migrations to a fresh database,
`migrate diff` to `schema.prisma` is **empty** (MEASURED); applied to the dev and test databases.

| Table | Keys and integrity |
|---|---|
| `campaigns` | composite tenant FKs to workspace, **topic** and **clone source**; `current_version_id` / `current_execution_id` FKs keyed with the campaign id (a pointer can only name THIS campaign's rows); CHECKs: name 1–200, description ≤ 1,000, channel, purpose, 7 statuses, draft JSON shapes, version ≥ 1, not its own clone; indexes `(workspace_id, status, updated_at DESC, id DESC)`, `(workspace_id, created_at DESC, id DESC)`, GIN trigram on name |
| `campaign_versions` | FK to the campaign (composite tenant); `UNIQUE (campaign_id, number)`; CHECKs: number ≥ 1, schema id, `snapshot->>'schema' = schema`, sha-256 hex hash, reason; **insert-only** (no UPDATE grant + `BEFORE UPDATE` → `app.reject_update()`) |
| `campaign_executions` | FK to the campaign (composite tenant) and to the version **of the same campaign**; `UNIQUE (campaign_id, run_number)`; partial uniques `(version_id) WHERE run_kind = 'one_time'` and `(campaign_id) WHERE status IN (active)`; partial `(send_at) WHERE status = 'pending'`; CHECKs: run kind, 7 statuses, paused ⇔ paused_phase, counts ≥ 0, failure class/code pair, health, lease pair; identity columns frozen by trigger (also for the owner) |
| `campaign_recipients` | FK to the execution (composite tenant) and to the contact (composite tenant); `UNIQUE (execution_id, contact_id)`; CHECKs: 9 statuses (§7.1 enumerates 9; "10" in §12.4 was a miscount), attempts ≥ 0, lease pair; identity frozen by trigger. **No row is created by 6.5–6.8.** |

`audience_snapshot_id` is an opaque reference with no foreign key across bounded contexts (contract §12.3).

**Security (MEASURED, `packages/db/test/campaigns.test.ts`, 11 tests):**

| Check | Result |
|---|---|
| RLS | all 4 tables enabled + forced, one `FOR ALL` workspace policy with USING and WITH CHECK |
| Grants (4 roles × 4 tables × 7 privileges) | `workeasy_app`: SELECT, INSERT only (+ column UPDATE); reporting, identity, audience-count maintenance role: none; PUBLIC: none; **no DELETE/TRUNCATE for anyone at runtime** (contract §14.4) |
| Column UPDATE grants | draft, status, pointers, timestamps, version, execution system columns; **not** ids, tenant keys, channel, purpose, clone source, creator, version snapshot/number/hash, execution campaign/version/run number/initiator, recipient execution/contact |
| Cross-tenant (raw SQL as `workeasy_app`) | A sees 0 of B's campaigns/versions/executions/recipients; UPDATE of B rows affects 0 rows; inserts labelled with B refused (42501); mismatched org/workspace and org-only contexts see nothing |
| Composite keys | A cannot reference B's topic, campaign, version or contact (23503); a current-version pointer to another campaign's version is refused (23503) |
| Constraints | 9 representative CHECK violations refused (23514) |
| Immutability | version UPDATE refused for the runtime role (42501) **and** the owner (trigger, 42501); campaign channel and execution run number frozen for the owner |
| Uniqueness under concurrency | 6 concurrent inserts of version 1 → exactly 1 succeeds, 5 × 23505; 3 concurrent active executions → exactly 1; one-time version, run number and recipient uniqueness enforced |
| Optimistic concurrency | two conditional updates on the same row version → exactly one applies |
| Search function | bound to the caller's workspace, LIKE wildcards escaped, not executable by PUBLIC/reporting |

Existing suites: the security-invariant suite passes with the new tables (forced RLS everywhere, no tenant-key UPDATE).

Observation (INFERRED, not a defect of this design): unique indexes are checked without RLS, so an insert colliding
with another tenant's row (e.g. a foreign version id already executed) reports 23505 instead of 23503. Exploiting it
needs an already-known foreign UUIDv7, and no API accepts raw version/execution ids for inserts.

## 3. 6.6 — draft API

Routes (contract §15 rows 1–9, 18–19), all under `/v1/workspaces/{workspaceId}/campaigns`, strict shared Zod
request contracts (6.4), explicit response schemas in OpenAPI (generated from the shared view schemas), stable errors:

| # | Route | Permission | Concurrency / idempotency |
|---|---|---|---|
| 1 | `GET /capabilities` | campaigns.read | — |
| 2 | `GET /` | campaigns.read | keyset (updated_at DESC, id DESC); filters status[], channel, topicId, q (definer search), deleted |
| 3 | `GET /counts` | campaigns.read | one grouped query |
| 4 | `POST /` | campaigns.create (+ topics.read with topicId) | Idempotency-Key (claim-first, database-backed: survives multiple API instances) |
| 5 | `GET /{id}` | campaigns.read | — |
| 6 | `PATCH /{id}` | campaigns.update (+ lists.read / tags.read / topics.read for added sources or a topic — `draftChangePermissions`) | `expectedVersion` checked by the domain before any outcome; conditional `UPDATE … WHERE version = ?` |
| 7 | `DELETE /{id}` | campaigns.delete | `expectedVersion`; soft delete; no-op if deleted |
| 8 | `POST /{id}/restore` | campaigns.delete | no-op if not deleted |
| 9 | `POST /{id}/clone` | campaigns.create (+ campaigns.read) | Idempotency-Key |
| 18 | `GET /{id}/versions` | campaigns.read | keyset |
| 19 | `GET /{id}/versions/{versionId}` | campaigns.read | snapshot validated on read |

Every command locks the campaign row, lets the domain decide (`decideCommand`: version → deleted rule → matrix), and
writes the change, its domain event (transactional outbox) and its audit record in one transaction. A PATCH that
changes nothing after a successful version check writes and emits nothing (stale is still `version_conflict`).
Readiness and `allowedActions` / `blockedActions` are computed per view from the domain; nothing is stored.

**Supporting changes:** 16 campaign event types registered in the event catalogue against the 6.4 shared payload
schemas (strict; the catalogue is the outbox's validation gate — registration had to precede 6.6's events; the
catalogue/PII-scan milestone 6.10 keeps its other scope); 9 campaign audit actions; `CAMPAIGN_DELIVERY_MODE` config
resolved by the existing domain guard (boot fails on `test` outside NODE_ENV=test and on `live`); `AppError` can carry
pre-flight findings (for 6.8). The campaigns module receives Audience ports only through `CampaignsModule.forRoot`
from the application module (boundary rules unchanged and passing).

**Tests (MEASURED, `apps/api/test/campaigns-drafts.test.ts`, 11 tests):** capabilities; create (view, readiness,
actions, `campaign.created` with `clonedFrom: null`, audit); strict bodies (workspaceId / orgId / ownerId / status in a
body → 400); disabled channels → `CHANNEL_NOT_AVAILABLE`; foreign topic → 400 without leaking database text;
Idempotency-Key replay and conflict; RBAC (viewer read-only; editor edits; custom role denied topic and new list
sources, denials audited, change not applied); PATCH stale (also as a no-op) → 409, current no-op writes nothing,
4 concurrent writers → exactly 1 success; whole-field replacement and findings; event payload carries field names only
(no subject, body, sender text); delete/restore with versions, no-ops, list/counts exclusion, read-only while deleted,

## 6. BLOCKER — 6.7 pre-flight needs Audience facts that no approved port provides

**Evidence.**
- Contract §3.1 `PreflightResult.estimate`: "eligibility evaluated on a **uniform sample ≤ 2,000**"; findings
  `NO_ELIGIBLE_RECIPIENTS` / `LOW_ELIGIBLE_SHARE` come from that estimate; `TOPIC_UNAVAILABLE` (deleted, archived or a
  category) needs the topic's status.
- Architecture §9 row 6.7 consumes "Resolution.count, Eligibility v1.1" only.
- The frozen `AudienceResolution` v1 port (Audience contract §9.4; `packages/audience-core/src/ports.ts`) offers
  `validate`, `count`, `capture`, `page`, `releaseByKey`, `listUnreleased`, `listReleasedUnpurged` — **no sampling and
  no topic status**. `EligibilityEvaluator.evaluate` needs contact ids and only throws for an unknown topic.
- The instruction forbids Campaign code from querying contacts, memberships or topics directly.

**Why it matters.** Without member ids there is no eligibility estimate; without topic status there is no
`TOPIC_UNAVAILABLE`. Using `capture` + `page` to sample would create an execution-owned snapshot (owner kind is
`campaign_execution` only) for a read-only check, require release, and cost 15–60 s at 5M against a 2 s target.
6.8's `schedule` / `send_now` run the same pre-flight engine (contract §3.1: "the same engine runs at schedule"), so
6.8 cannot be completed without it either.

**Options.**
1. **Additive Audience Resolution v1.1 extension (recommended):** `sample(scope, def, { size ≤ 2,000 })` → a uniform
   sample of live member ids plus the exact count in one statement (no snapshot), and a topic-status read (e.g.
   `validate` accepting an optional `topicId`, or `topicStatus(scope, topicId)`). Implemented in audience-infra, wired
   by the Audience composition root, consumed by Campaigns through the port. Requires approval because it extends the
   frozen Audience contract §9.4.
2. Amend the campaign contract: pre-flight without the eligibility estimate (`estimate.eligibleEstimate` absent,
   `NO_ELIGIBLE_RECIPIENTS` / `LOW_ELIGIBLE_SHARE` deferred to start time) and topic status from Eligibility's
   unknown-topic error only (archived topics undetected until start). Weaker pre-flight.
3. Sample through `capture` + `page` + `releaseByKey` — **not recommended** (misuses the snapshot lifecycle; violates
   the 2 s target at scale).
